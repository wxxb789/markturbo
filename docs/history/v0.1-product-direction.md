# Historical v0.1 Product Direction

> **Historical document.** This file preserves the original implementation
> brief and the reasoning that produced the current application. It is not a
> current product contract. [PRODUCT.md](../../PRODUCT.md) governs current user,
> scope, success measures, data policy, and release priorities. Every directive,
> requirement, checklist, and completion criterion below is historical evidence
> unless the current contract or a numbered goal adopts it explicitly.

Build a **native, local-first desktop application** using **Rust + GPUI + `longbridge/gpui-component`** for reading, rendering, lightly editing, translating, and managing Markdown-centric AI artifacts.

The product is not merely another Markdown editor.

Its core thesis is:

> **Markdown is becoming the shared interface between humans and AI agents.**

AI systems increasingly consume and produce artifacts such as:

* `README.md`
* `AGENTS.md`
* `CLAUDE.md`
* `SKILL.md`
* agent instructions
* prompts
* specifications
* plans
* research notes
* memory/context documents
* `.cursor/rules/*`
* Agent Skills
* MDX documents

The application should treat these as first-class artifacts rather than generic text files.

The product can be thought of as an:

> **AI-native Markdown Workspace / Agent Skills Workbench**

A useful guiding sentence for every product and architecture decision is:

> **This is not a Markdown editor with AI features. It is a native workspace for Markdown as the interface between humans and AI agents.**

---

# 1. Product principles

The implementation must follow these principles.

## 1.1 Native-first, not native-only

The application itself must be genuinely native:

* Rust
* GPUI
* `gpui-component`
* native filesystem integration
* native windowing
* native navigation
* native editor
* native Markdown rendering whenever practical

Do **not** build an Electron-style web application wrapped in a desktop shell.

However, do not attempt to reimplement the entire web rendering ecosystem in Rust.

Use two rendering paths:

1. **Native renderer**
2. **WebView renderer**

The native renderer is the fast path.

The WebView renderer is the compatibility path.

---

## 1.2 Local-first

The filesystem is the source of truth.

Opening a directory should create a workspace directly.

Do not introduce a proprietary workspace/database/notebook document format for v0.1.

Example:

```text
workspace/
├── README.md
├── AGENTS.md
├── CLAUDE.md
├── docs/
├── prompts/
├── skills/
├── .agents/
│   └── skills/
├── .claude/
│   └── skills/
└── .cursor/
```

Files edited by this application must remain ordinary files that can immediately be consumed by:

* Codex
* Claude Code
* Cursor
* OpenCode
* DeepSeek Harness
* shell tools
* Git
* any other agent or editor

No import/export step should be required.

---

## 1.3 Markdown is a source format, not an internal database format

Preserve original Markdown whenever possible.

Do not silently normalize/reformat documents when merely opening or previewing them.

Editing should produce predictable textual changes.

The document engine may maintain parsed structures internally, but the source file remains authoritative.

---

## 1.4 Lean architecture

Prefer a small number of strong abstractions over many layers.

Avoid speculative framework-building.

Do not build a generic plugin platform in v0.1.

Instead, make the internal architecture extensible enough that additional renderers and document types can be added without redesigning the application.

---

# 2. Required v0.1 user experience

A user should be able to:

1. Launch the application.
2. Open a local directory as a workspace.
3. Browse files through a native file tree.
4. Open multiple Markdown/MDX files in tabs.
5. Read Markdown using a high-performance native renderer.
6. Switch the same document to WebView rendering.
7. Open source and preview side by side.
8. Lightly edit the Markdown source.
9. See preview updates after edits.
10. Render diagrams and mathematical notation.
11. Open and preview MDX.
12. Translate selected text, blocks, or documents.
13. Discover Agent Skills in the workspace.
14. Browse skills through a dedicated Skills view.
15. Inspect skill metadata and `SKILL.md`.
16. Save changes directly to normal filesystem files.
17. Detect external file changes and refresh safely.

The application should feel closer to a fast native document browser/workbench than a full IDE.

# 3. Core UI modes

Every supported document should conceptually support these views when applicable:

```text
Source
Native
Web
Split
```

## Source

Native lightweight editor.

## Native

GPUI-native rendering.

Optimized for:

* startup latency
* scrolling
* low memory usage
* text selection
* large documents
* integration with the rest of the native UI

## Web

WebView rendering.

Optimized for:

* compatibility
* MDX
* arbitrary HTML
* Mermaid
* browser-based rendering libraries
* complex mathematical rendering
* interactive content

## Split

At minimum:

```text
Source | Preview
```

Preview may use Native or Web rendering.

The architecture should not prevent future layouts such as:

```text
Native | Web
Original | Translation
```

# 4. Document Engine

Create a central **Document Engine** independent of GPUI rendering code.

Do not make GPUI widgets themselves the source of document semantics.

Conceptually:

```text
Filesystem
    │
    ▼
Document Engine
    │
    ├── source
    ├── parsed structure
    ├── metadata
    ├── frontmatter
    ├── headings
    ├── links
    ├── code blocks
    ├── diagrams
    ├── diagnostics
    └── document type
```

Then:

```text
Document Engine
      │
      ├── Editor
      ├── Native Renderer
      ├── Web Renderer
      ├── Outline
      ├── Translation
      └── Skill Inspector
```

The Document Engine should not depend directly on GPUI.

This is important because it may later be reused by:

* CLI tooling
* MCP tools
* agent tools
* headless rendering
* indexing
* automated skill inspection

Do not implement those additional products now.

Just avoid coupling the document model to UI widgets.

# 5. Renderer architecture

Do not hard-code each diagram technology into the Markdown renderer.

Introduce a small renderer registry / block-rendering abstraction.

Conceptually:

```rust
enum BlockKind {
    Markdown,
    Code(Language),
    Math,
    Diagram(DiagramKind),
    Html,
    Mdx,
}
```

And:

```text
BlockRendererRegistry
├── Markdown
├── Code
├── Mermaid
├── D2
├── PlantUML
├── LaTeX
└── ...
```

The exact Rust API may differ after inspecting the libraries and implementation constraints.

The important architectural property is:

> Adding another fenced-block renderer should not require modifying the core Markdown parser/rendering architecture.

Future renderers might include:

* Graphviz
* Vega
* ECharts
* Typst
* Pikchr
* svgbob
* nomnoml

Do not implement these unless doing so is trivial after the required renderers are complete.

---

# 6. Required diagram and math support

v0.1 must support live preview for at least:

* Mermaid
* D2
* PlantUML
* LaTeX/math

Prefer deterministic local rendering where practical.

Avoid requiring cloud services for ordinary rendering.

If one technology has unavoidable external-runtime requirements, isolate that dependency behind its renderer implementation rather than infecting the document architecture.

Rendering failures must not crash the application.

Instead display an inline diagnostic associated with the corresponding block.

Example:

```text
Mermaid rendering failed

Unexpected token at line 7
```

Preserve the original source.

---

# 7. Native renderer vs Web renderer

Do not attempt feature parity between the two renderers.

That is explicitly not a goal.

## Native renderer

Prioritize:

* Markdown typography
* headings
* lists
* quotes
* tables
* links
* code blocks
* syntax highlighting
* images
* math where practical
* rendered diagram results
* fast scrolling
* large files
* low overhead

## Web renderer

Prioritize:

* maximum Markdown compatibility
* MDX
* HTML
* Mermaid/browser ecosystem
* interactive content
* CSS-based themes
* advanced math
* JSX/component rendering

The conceptual rule is:

> **Native is the fast path. WebView is the compatibility path.**

Do not recreate React/MDX/browser semantics in native Rust.

---

# 8. MDX

MDX is a first-class document type.

Do not pretend that MDX is merely Markdown with a few additional tags.

It combines concepts such as:

```text
Markdown
+
JSX
+
ES modules
+
JavaScript expressions
+
component runtime
```

Therefore:

## Native mode

Native mode should understand enough MDX structure to:

* edit the file
* identify Markdown blocks
* identify JSX blocks
* identify imports/exports
* identify expressions
* build an outline where possible
* avoid corrupting the document

Unsupported dynamic components may be represented as native placeholders.

Example:

```text
┌──────────────────────┐
│ <RevenueChart />     │
└──────────────────────┘
```

## Web mode

WebView is the canonical full-fidelity MDX preview path.

Conceptually:

```text
MDX
 ↓
compile
 ↓
JS/JSX/ESM
 ↓
component runtime
 ↓
WebView
```

Use a well-supported existing MDX ecosystem rather than implementing an MDX compiler from scratch.

Security matters.

MDX execution must eventually have an explicit trust model because MDX can contain executable code.

For v0.1, at minimum distinguish trusted local content from potentially untrusted content and avoid silently executing arbitrary code without considering the security boundary.

# 9. Lightweight editing

This is not a full IDE.

Use the editor capabilities available in the GPUI/gpui-component ecosystem where practical.

Required:

* text editing
* Markdown syntax highlighting
* MDX syntax awareness if practical
* undo/redo
* search
* save
* keyboard navigation
* large-file usability
* source ↔ preview synchronization where reasonably achievable

Do not build:

* LSP infrastructure
* refactoring engine
* debugger
* terminal
* source-control UI
* full programming IDE features

unless an existing component makes one effectively free.

# 11. Agent Skills are first-class documents

Do not treat `SKILL.md` merely as another Markdown filename.

Introduce a Skill model.

A skill is conceptually a directory containing:

```text
some-skill/
├── SKILL.md
├── scripts/
├── references/
├── assets/
└── ...
```

Parse YAML frontmatter in `SKILL.md`.

At minimum understand and validate the common metadata fields required by the Agent Skills ecosystem, especially:

```yaml
---
name: ...
description: ...
---
```

Do not invent a proprietary skill format.

Aim for compatibility with the emerging **Agent Skills / Vercel `skills` ecosystem** and common agent implementations.

Before implementing the parser/discovery rules, inspect the latest relevant specifications and repositories rather than relying on stale assumptions.

---

# 12. Skills Explorer

Create a dedicated Skills view.

Example:

```text
Skills
├── define-goal
├── github
├── pdf
├── slides
└── research
```

Selecting a skill should expose useful structure such as:

```text
Skill

Name
Description
Location
Metadata

Files
├── SKILL.md
├── scripts/
├── references/
└── assets/
```

Then display/render `SKILL.md`.

Automatically discover common skill directories where appropriate, including ecosystem conventions such as:

```text
skills/
.agents/skills/
.claude/skills/
```

Do not hard-code the entire product to any single agent vendor.

The architecture should allow additional discovery conventions to be added cheaply.

---

# 13. Agent instruction documents

Design the document-type model so the application can recognize common AI instruction files such as:

```text
AGENTS.md
CLAUDE.md
SKILL.md
.cursor/rules/*
*.instructions.md
```

For v0.1, recognition and specialized labeling/metadata are enough.

Do not build a full instruction-resolution engine unless the required core application is already complete.

However, ensure the architecture does not prevent a future feature such as:

```text
Effective Agent Context

repo/AGENTS.md
        ↓
src/AGENTS.md
        ↓
current file
```

This future direction is strategically important, but not required for v0.1.

# 14. Translation

Translation must be document-aware rather than blindly translating the complete raw Markdown string.

Support:

* selected text translation
* block translation
* full-document translation

Preserve, where appropriate:

* fenced code
* inline code
* URLs
* link targets
* file paths
* identifiers
* frontmatter keys
* diagram source
* mathematical notation
* markup structure

For example, translate prose while keeping this unchanged:

```rust
let value = String::new();
```

The architecture should expose translation through an abstraction such as:

```text
TranslationService
```

rather than coupling the UI directly to one vendor.

Do not hard-code a specific LLM/API provider into the document model.

A provider implementation may be used for v0.1, but the boundary must remain explicit.

Future UI should be able to support:

```text
Original | Translation
```

without redesigning the document architecture.

# 15. Filesystem behavior

Required:

* open directory
* file tree
* open file
* save
* Save As when appropriate
* detect external modifications
* safe reload
* filesystem watching
* normal UTF-8 handling
* predictable newline handling
* avoid unnecessary rewriting of untouched content

When a file changes externally, never silently overwrite those changes with stale editor state.

Conflict handling may be simple in v0.1 but must be safe.

---

# 16. Performance expectations

This application's reason for using GPUI is partly native performance.

Do not accidentally erase that advantage with architecture that sends every Markdown operation through a WebView.

Native Markdown must remain native.

Pay particular attention to:

* startup
* workspace opening
* large Markdown documents
* scrolling
* incremental editing
* preview updates
* unnecessary allocations
* duplicate parsing
* blocking work on the UI thread

Prefer incremental work and caching when complexity is justified.

Avoid premature micro-optimization, but do not choose fundamentally inefficient architecture.

As an initial acceptance target, verify usability with at least:

* a small ordinary Markdown document
* a diagram-heavy document
* an MDX document
* a `SKILL.md`
* a Markdown file around 10K lines
* a Markdown file around 100K lines

The 100K-line case does not need every advanced live-preview feature to be instantaneous, but the application must remain responsive and usable.


Treat this as an architectural direction, not a requirement to reproduce these boxes/classes literally.

Prefer fewer abstractions if the same boundaries can be preserved more elegantly.

# 19. Implementation approach

Before writing substantial code:

1. Inspect the latest GPUI APIs.
2. Inspect the latest `longbridge/gpui-component` source and examples.
3. Identify reusable existing components for:

   * editor
   * Markdown
   * HTML
   * WebView
   * dock
   * tabs
   * tree/file explorer
   * syntax highlighting
4. Inspect the current MDX ecosystem and choose an existing compiler/runtime.
5. Inspect current Agent Skills/Vercel `skills` conventions.
6. Determine practical local rendering strategies for Mermaid, D2, PlantUML, and LaTeX.
7. Write a concise architecture note describing the selected boundaries and major dependency choices.
8. Then implement the smallest vertical slice.

Prefer source-code inspection over assumptions about library APIs.

Do not create duplicate infrastructure already available from `gpui-component`.

# 20. Vertical implementation order

Implement end-to-end capability rather than building every subsystem horizontally.

Recommended order:

### Slice 1 — Native Markdown

```text
Open folder
→ File tree
→ Open .md
→ Edit
→ Native preview
→ Save
→ filesystem watcher
```

### Slice 2 — Dual renderer

```text
Document
→ Native
→ Web
→ Source
→ Split
```

Prove that one document model can drive both rendering paths.

### Slice 3 — Extensible rendered blocks

Add:

```text
LaTeX
Mermaid
D2
PlantUML
```

through the renderer abstraction.

### Slice 4 — MDX

```text
Open MDX
→ Edit
→ understand structure
→ WebView preview
```

### Slice 5 — Skills

```text
Discover skills
→ parse SKILL.md
→ validate metadata
→ Skills Explorer
→ render/edit
```

### Slice 6 — Translation

```text
selection
block
document
```

Do not begin with all six subsystems partially implemented.

Complete each vertical slice enough to validate its architecture before expanding.

# 23. Decision rules

When uncertain, follow these rules:

1. Prefer filesystem conventions over proprietary state.
2. Prefer GPUI native UI over WebView UI.
3. Prefer Native rendering for ordinary Markdown.
4. Prefer WebView when browser semantics are genuinely required.
5. Prefer existing mature parsers/renderers over custom implementations.
6. Prefer one shared document model over parallel Native/Web document models.
7. Prefer extensible block rendering over Mermaid/D2/etc. special cases.
8. Prefer vertical slices over subsystem-first development.
9. Prefer type-safe Rust boundaries that make invalid states difficult to represent.
10. Prefer less code when it preserves correctness and clarity.
11. Avoid abstractions without a current architectural need.
12. Do not broaden scope merely because an adjacent feature seems useful.

---

# 24. Stop condition

Do not stop to ask the user about routine implementation details that can be resolved from:

* upstream source
* official documentation
* existing repository conventions
* a reversible engineering decision

Make the best technically justified choice and document it.

Stop and ask only if continuing would require one of the following:

* materially changing the product goal
* introducing a proprietary storage format
* abandoning GPUI/gpui-component as the primary native stack
* removing one of the required v0.1 capabilities
* introducing an unavoidable external/cloud dependency for a core local workflow
* making an irreversible security/product decision with multiple materially different choices

Otherwise, continue through implementation and verification.

# Historical product direction

The immediate goal is **not** to create the most feature-rich Markdown application.

The goal is to establish a small but sound foundation for a new category:

> **A native workspace where Markdown is treated as the source code of human–AI collaboration.**

The architecture should make the following future evolution possible without requiring it now:

```text
Markdown Workspace
        ↓
Agent Skills Workbench
        ↓
Agent Instruction Inspector
        ↓
Effective Context Inspector
        ↓
Human ↔ Agent shared workspace
```

Keep the core lean enough that this evolution remains possible rather than burying it under premature features.
